# План: торговый бот HYPEUSDT (Bybit, бессрочный USDT-контракт)

Документ фиксирует итог этапа 0: решения, архитектуру и порядок работы.
Источники фактов об API: официальный репозиторий документации
`bybit-exchange/docs` (состояние на 2026-09-29) и исходный код pybit 5.17.0
(PyPI, 2026-07-14).

## 1. Принятые решения

| Параметр | Значение |
|---|---|
| Инструмент | HYPEUSDT, `category=linear` |
| Аккаунт | российский; в официальном списке Bybit нет домена `.ru`, поэтому используется глобальный `api.bybit.com` (запасной официальный домен — `api.bytick.com`) |
| Тип аккаунта | Unified Trading Account, отдельный субаккаунт ровно с 10 USDT |
| Режим позиции | one-way (одна позиция на инструмент: либо лонг, либо шорт) — режим Bybit по умолчанию, бот проверяет его при старте |
| Маржа | изолированная (в UTA включается на весь субаккаунт: `/v5/account/set-margin-mode` → `ISOLATED_MARGIN`) |
| Депозит | 10 USDT |
| Максимальное плечо | 50 |
| Риск на сделку | 5% капитала |
| Дневной лимит убытка | 25%, день считается по UTC (00:00 UTC) |
| Максимальная просадка | 80% от пика капитала → закрыть всё, остановиться |
| Пауза после серии убытков | 4 убыточные сделки подряд → пауза 24 часа |
| Пополнения/выводы во время работы | не предполагаются |
| Направления | лонг и шорт |
| Триггер стопа | `LastPrice` (как в бэктесте); ликвидация (по mark-цене) всегда дальше стопа с запасом |
| Комиссии | стандартный (начальный) уровень; точные ставки берутся из `/v5/account/fee-rate` |
| IP | постоянный, Россия → ключ API привязывается к IP |
| Компьютер | Windows, Docker не установлен → основной способ запуска: Python + `.bat`-файлы; Dockerfile — дополнительно |
| Код | папка `hype-bot/` в этом репозитории |
| Отложенные данные | последние 6 месяцев истории не используются при подборе |
| Демо | минимум 2 недели (окончательный срок — на ваше решение) |
| Сравнение с buy & hold | у стратегии выше и Sharpe, и Calmar на отложенном периоде |

## 2. Важные факты из документации

- Ордер на вход несёт стоп сразу: `stopLoss`, `tpslMode=Full`, `slTriggerBy`.
  Ответ на создание ордера — только подтверждение приёма; результат
  подтверждается через WebSocket (`order`, `execution`, `position`).
- Рыночный ордер исполняется как IOC-лимит с защитой цены; при нехватке
  ликвидности может не исполниться. Есть `slippageToleranceType/slippageTolerance`.
- `orderLinkId` — до 36 символов `[A-Za-z0-9_-]`, уникален; повтор → `110072`.
- Лимиты: 600 запросов / 5 с на IP (иначе 403 и бан ≥10 мин);
  `create/amend/cancel` для linear — 10/с; `position/list`, `wallet-balance` — 50/с.
- DCP (отмена ордеров при обрыве) доступна только институциональным клиентам →
  главная защита — стоп на стороне биржи.
- Демо: REST `api-demo.bybit.com`, приватный WS `stream-demo.bybit.com`,
  публичные данные — с обычного `stream.bybit.com`; ордера хранятся 7 дней;
  баланс демо можно уменьшить через API (будет 10 USDT).
- Ключ без привязки к IP перестаёт работать через 90 дней. Нужные права:
  «Контракты → Ордера, Позиции». Вывод и переводы — не включать.
- IP из США и материкового Китая получают 403.
- pybit 5.17.0: WebSocket по умолчанию прекращает переподключаться после 10
  попыток (нужно `retries=0` + свой сторож); публичный WS с флагом `demo`
  ведёт на `stream-demo`, где публичных данных нет; сетевые ошибки HTTP по
  умолчанию не повторяются — повторы делаем сами с идемпотентностью по `orderLinkId`.

## 3. Ограничения, известные заранее

1. История HYPEUSDT на Bybit — меньше 2 лет (листинг — конец 2024; точная дата
   `launchTime` будет взята из API). Решение: вся доступная история + проверка
   найденных правил на других ликвидных контрактах (проверка, не подбор).
2. ≥100 сделок за 6 месяцев отложенных данных ≈ ≥4 сделки в неделю →
   реалистичные таймфреймы 15m–1h, где сильнее влияние комиссий.
3. Минимальная стоимость ордера ограничивает ширину стопа:
   `макс. стоп = риск_USDT / мин. ордер`. Сделки, не проходящие минимум,
   пропускаются; риск ради них не увеличивается.
4. Если ни одна стратегия не пройдёт критерии приёмки — это будет сказано прямо.

## 4. Архитектура

```
              Bybit: REST api(-demo).bybit.com · WS stream.bybit.com / stream-demo
                    ▲ REST (ордера, сверка)           │ WS (свечи, ордера, позиции)
        ┌───────────┴──────────┐          ┌──────────▼───────────┐
        │ BybitClient          │          │ WS-супервизор        │
        │ лимитер на эндпоинт, │          │ переподключение,     │
        │ повторы с задержкой, │          │ сторож свежести,     │
        │ классификация retCode│          │ догрузка пропусков   │
        └───────────▲──────────┘          └──────────┬───────────┘
                    │                                │ события → очередь
        ┌───────────┴────────────────────────────────▼───────────┐
        │ Engine — однопоточный цикл событий (общий для 3 режимов)│
        │  Strategy (чистая функция) → RiskManager → Broker      │
        │  Broker = SimBroker (backtest) | BybitBroker (demo/live)│
        └───────┬──────────────────────────┬─────────────────────┘
          SQLite: ордера, сделки,       JSON-логи
          капитал, риск-состояние       (секреты вырезаются)
```

```
hype-bot/
  config/config.example.yaml   # все параметры риска и стратегии
  .env.example  .gitignore  Dockerfile  README.md
  bot/
    config.py                  # загрузка и проверка YAML
    exchange/                  # client.py, retcodes.py, ws.py, instrument.py
    data/                      # downloader.py, store.py, quality.py
    strategy/                  # base, breakout, momentum, meanrev, volbreak, regime
    risk/                      # sizing.py, guards.py
    engine/                    # core.py, sim_broker.py, bybit_broker.py, reconcile.py
    storage/                   # db.py (SQLite)
    cli.py                     # data | backtest | research | run | status | kill | resume | report
  research/  reports/  tests/
```

Поток сделки: закрытие свечи → сигнал → проверки риска (лимиты, просадка,
серия, свежесть данных, сверка) → объём от риска и стопа, плечо с запасом до
ликвидации → запись намерения в SQLite → рыночный ордер со стопом и
`orderLinkId` → подтверждение по WS/REST → проверка, что стоп стоит и
`liqPrice` дальше стопа, иначе — довнесение маржи или закрытие.

Перезапуск: загрузка состояния из SQLite, сверка позиций, ордеров, исполнений
за время простоя и баланса; при расхождении — безопасный режим (без новых
входов, у позиции обязательно стоп).

Аварийная остановка: команда `kill` (работает напрямую через REST) — отмена
ордеров, закрытие позиции reduce-only ордером, флаг остановки в БД, который
снимается только командой `resume`.

Режим live: `live.enabled: true` в конфиге + флаг `--live` + ввод фразы
подтверждения при старте; первая фаза — минимальный объём.

## 5. Этапы

| Этап | Результат | Коммит |
|---|---|---|
| 0 | этот план | `stage 0` |
| 1 | данные: 1m свечи (последняя и mark-цена), финансирование, параметры инструмента, лимиты риска, комиссии; отчёт о качестве | `stage 1` |
| 2 | событийный бэктестер, тесты на отсутствие заглядывания в будущее | `stage 2` |
| 3 | 4 типа стратегий + фильтр режима, walk-forward, отложенные 6 мес., проверки устойчивости, отчёт | `stage 3` |
| 4 | торговый движок (backtest/demo/live), риск-модуль с тестами, SQLite, логи, README, Dockerfile | `stage 4` |
| 5 | демо ≥2 недель, ежедневные отчёты и сравнение с бэктестом | `stage 5` |
| 6 | live только после явного «да», сначала минимальный объём | `stage 6` |

После каждого этапа — остановка и ожидание подтверждения.
